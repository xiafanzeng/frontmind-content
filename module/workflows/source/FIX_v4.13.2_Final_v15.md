# Workflow v15 更新说明

本版只改变新建 P01、P02 的写作与最后编辑。行业、名单、分档、篇幅仍来自案例配置；P0、其他 Pattern、已冻结请求及历史任务保留原流程。

## 正文与 Prompt

- 蓝图先依据 article_brief 确定全文范围，题目需求可以只作开篇入口。取舍直接落实到作者材料中：未选项目和重复别名不再传入，只有名称的项目简述，有具体工作、设置和服务细节的内容才重点展开。sections 写清要让读者认识到的具体特点，资料分类不自动成为文章栏目。
- DeepSeek 负责初稿和 E8 编辑。E8 可以重分主次、合并重复、拆解长句；正常需求和用途说明可以保留。
- E8 把重复需求、反复咨询提醒、列表后的同义释义一并作为内容重复处理。当前 article_brief 决定介绍层次，题目不把整篇机构介绍缩成单一项目咨询。
- 加入跨行业完整段落示例，示范怎样以具体特点组织信息、自然交代使用情境。一般需求与感受可以展开，不冒充真实采访或接待案例。
- count_article 只返回正文字符数。首次按全文篇幅安排足够内容，测字后若差距较大则重分内容、重写相关完整段落，不在短稿逐句补释义。篇幅进入要求范围即可，不提供字数缺额任务，不要求删减后等量补回。
- 实跑后进一步区分初稿与交付篇幅：初稿按交付上限再多约一成来安排内容，E8通过合并和取舍完成交付范围；余量必须来自完整的原始业务描述。蓝图选中的主要信息组以原文短段保留，不再二次压成摘要。最终P01、P02字数范围不变。
- XTY 只接收当前完整稿和必要写作要求，用 needs_revision、comments、local_edits 提交结果。多段项目目录、逐词释义、资料旁白和重复邀请也属于需要作者处理的内容组织问题，不能只挑几个病句便放行。没有语言评分、禁词表或新增确认页。
- 最后句级校对先检查主谓宾搭配、介词完整性和并列项的修饰关系，特别处理资料拼接后的长句；不能只删显眼赘词而放过句法不成立的地方。修通表达并保留具体信息，不把校对等同于缩句。
- 作者返工时以当前委托为准。审阅建议负责指出问题，不能把开篇需求重新变为全文唯一主线，或取消委托允许的独立内容。

## 最后编辑

正常路径：蓝图 → DeepSeek 初稿 → E8 → XTY 通过或句级微调 → 标题 → 导出。

需要结构返工时：XTY 意见 → DeepSeek 一次返工 → 独立 article_polish 阶段读取返工全文 → 标题 → 导出。仍有主要问题则保留待修改，不自动完成。

若 article_polish 仍要求修改，原任务保留返工稿与审阅意见，不产生最终稿或新标题。普通 continue 不会自动再跑作者；当前版本也不支持对这一未完成任务使用 --manuscript-edits 或 --blueprint-edits 继续正文修订。需要重新写作时，保留原任务，在新目录通过 scripts/frontmind article 从原始资料启动新任务，再修改和确认新蓝图；本包案例可用 scripts/run_taixin_v15_case.py --stage all 配合新的 --job-dir 重新生成。失败任务不能标记成 completed 来绕过这一边界。

局部替换必须在基稿唯一匹配、片段不重叠、不跨段，保护标题及加粗的主体和档名。替换错误直接报错。最后稿件绑定作者基稿、编辑结果与对应调用；标题、Word、Markdown 和后续修改统一读取该稿。

两篇案例的 case.json 以 body_character_range 明确最终正文范围，案例入口将其保存在任务 metadata。v15 的 article_finalize 与 article_polish 在 needs_revision=false 时，对应用全部 local_edits 后的实际全文计数；超范围的 submit_result 通过既有反馈路径返回实际字符数和允许范围，不返回缺额、不新增作者轮次。最终稿恢复及交付前也复核这一范围。旧版和未设置该字段的任务保持原行为；数字只来自案例配置，篇幅合格不代表语言质量合格。

## 程序与样例

主要修改位于 shared/writing_context_v15.py、shared/language_editor_v15.py，以及原运行器、HostTools 和正文续改接口。正式入口仍为 scripts/frontmind；两篇样例入口为 scripts/run_taixin_v15_case.py。

customer_inputs/taixin/v15 保存原始资料、案例委托、参考例文和 generated 结果。正文来源为 DeepSeek 基稿加 XTY 局部编辑；未由外层助手替写。开发失败调用及临时日志不打入发布包。

两篇案例共同读取原始官网项目介绍、机构介绍和项目表。官网项目快照中的业务做法与服务细节保留用于选材，不能仅因原网页含咨询入口，就把整份业务介绍排除；问答结构、咨询按钮和页尾提示不沿用为文章结构。

打包前复用已完成稿的真实调用与正文来源校验，拒绝模拟或未完成的链路。包内 final_source.result_file 指向同目录的审阅结果，正文字符串保持不变；字符数从核验后的实际终稿重新统计。

每阶段除用户 Prompt 外，还保存实际模型请求中的系统指令：DeepSeek 从 messages 的 system 内容提取，XTY 从 system_instructions 提取。同一指令跨轮次只保存一次；若实际指令不同，则另存编号文件。run.json 记录对应请求文件、调用编号及原文和包内文本哈希。恢复调用沿已记录的来源提取，零调用恢复不会用当前源码模板替代原指令；不复制完整请求、凭据或运行日志。

验证包括正常通过、局部编辑、结构返工后的再次阅读、错误替换、中断恢复、旧版本恢复、独立标题修改和导出正文一致性。Word 另行渲染逐页检查，语言质量另行阅读全文判断。
